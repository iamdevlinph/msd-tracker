# Testing Guidance

Read this reference for test changes, automated regression work, or validation that requires tests. Do not load it for unrelated documentation, tooling, release, deployment, or UI-only work. Visual-regression work also requires `.agents/skills/ui-style-preflight/SKILL.md`; feature behavior tests also require the owning feature plan routed from `PLANS.md`.

Use Vitest and Testing Library. Add `// @vitest-environment jsdom` to DOM tests; Node is default. Select focused regression tests by observable contracts, reported regressions, meaningful boundaries, and plausible costly failures. Use one representative case per necessary observable contract or reported regression; skip speculative edge cases, redundant permutations, implementation-detail assertions, and contrived or unreachable states. Retain boundary coverage only for an explicit requirement, past defect, or plausible security, trust-boundary, or data-loss failure. Run focused tests before broader suites.

Test observable production behavior through the narrowest real executable boundary. Prefer the public interface when practical; otherwise call the actual production function or module and assert inputs, outputs, state transitions, side effects, failures, or persisted results. Use a focused integration test when a contract spans components.

Do not treat source-file reads, string or regex presence, snapshots, symbol counts, private helpers, internal statement ordering, or duplicated test-local production logic as functional verification. Text assertions are appropriate only when the text is itself the observable contract, such as generated artifacts, CLI, help, or prompt output, serialization or protocol formats, externally consumed configuration, migration SQL, or required templates and instructions; assert only the smallest meaningful textual contract. If no real executable boundary exists, add the smallest justified local test seam, or preserve existing coverage and report when a behavioral replacement would require disproportionate, risky, or ambiguous restructuring.

Behavior tests must use test-owned fixtures or module mocks rather than importing mutable game datasets, including for fixture typing; direct live-data imports are reserved for dedicated dataset-validation tests. Do not introduce a test framework or low-value tests solely for coverage; when automation is impractical, explain why and perform the strongest targeted verification available. Mock browser boundaries and keep fixtures focused, subject to the escalation rules in `AGENTS.md`.

Treat existing tests as regression contracts. Preserve their assertions unless the requested behavior intentionally changes. When behavior changes, update only the affected tests and add coverage for the new contract; never weaken or delete tests merely to make the suite pass.
